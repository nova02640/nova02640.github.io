The previous post introduced the finished product ([Turning a 523-Lesson AI Engineering Course into a Level-Based Progress Site](/ai-engineering-quest-launch/)); this one records how it was built — including a logic flaw that only real testing could have caught, and several pitfalls I hit that "looked successful but were never actually verified."

The finished site is here: **https://nova02640.github.io/ai-engineering-quest/**

---

## 1. Topic Selection: First Confirm "What Not to Do"

The project started from an open-source course that really fit my taste: **AI Engineering from Scratch** — 523 lessons, 20 stages, and every lesson requires you to hand-write an algorithm and leave behind a reusable artifact.

My initial idea was the same as most people's: **build a learning website**. But before starting, I went and read the upstream repository, and the conclusion changed immediately — **the upstream already has a fully functional website**: all 523 lessons rendered online, a quiz after each lesson, local progress tracking, interactive charts, a glossary, learning paths, certification exam question banks, an interface in 12 languages, and the repository has commits every day.

If I built it the same way, the result would only be two problems: fewer features, and forever chasing the upstream.

**So the task definition changed from "build a learning website" to "build something the upstream doesn't have."** After listing the upstream's feature set item by item and comparing, the remaining gaps were clear:

| Upstream already has | Upstream doesn't have |
|---|---|
| Four checkboxes per lesson (read/built/ran/evidence) | A cross-level global progress view (levels, stage completion, badges) |
| `evidence` only records a "checked" timestamp | **Evidence retention** of commands / exit codes / output / artifacts |
| Quizzes generated by AI at runtime | A static question bank (offline-capable, repeatable, regression-testable) |
| A complete reading experience | Turning "each lesson delivers an artifact" into a portfolio |

The positioning was thus settled: **don't make courses; make the recording layer for the courses.**

---

## 2. Architecture: A Thin Layer, Not a Mirror

The second decision was equally important: **not a single word of course content enters my repository.**

The site takes only metadata — title, number, path, type, language, learning objectives, and file listings of `outputs/` and `code/`; all reading and exercises deep-link to the official original text.

The cost of this approach is an incomplete in-site reading experience (you have to jump out to read the lecture notes), in exchange for:

- **Extremely low maintenance cost**: upstream changes content daily, my site is unaffected
- **Completely different copyright nature**: citing metadata + deep links is a tool; copying full text is republication
- **Cleanly severable**: if upstream changes its license, just delete the metadata

The page structure became correspondingly lightweight — four static pages + one local save engine:

```
index.html        quest map (20 stages / 523 levels + HUD)
lesson.html       level page (four-step check-in / quiz / artifact registration)
boss.html         stage boss fight (12 questions)
portfolio.html    portfolio (export HTML / Markdown / JSON)
assets/store.js   save engine (localStorage + import/export)
data/course.json  metadata for all 523 levels
data/quiz.json    question bank
```

**No build step**: plain static files are uploaded directly by GitHub Actions, so the failure surface is smaller than any build-based site.

---

## 3. Data Pipeline: Taking Only the Fields I Need

Metadata is fetched in two layers:

**Full map (20 stages / 523 levels)**: use the GitHub Tree API to fetch all file paths in one call and derive the stage and level structure from the paths; then parse the lesson table in the upstream `README.md` to get each lesson's title, type (Learn / Build), and language. Of the 523 lessons, 438 can be parsed from the table; the remaining 85 are all in the final capstone stage (not in the table), so the path names serve as a fallback.

**Deep-dive stage details**: only for the stage I want to work on in depth, fetch `docs/en.md` per lesson and extract the level-one headings and the `## Learning Objectives` list. 31 lessons, about 492 KB, fetched in tens of seconds.

There's a small trade-off worth mentioning: I had once wanted to just download the whole repository archive, but in a network-restricted environment the package from the mirror channel was **truncated** (9.2 MB and 4.6 MB on two attempts, neither complete). Rather than fighting the download, it's better to fetch only the fields actually needed — **metadata from 31 small files is more reliable than a 46 MB dependency on the whole repository**.

## 4. Gameplay: Copy the Course's Criteria, Don't Invent Your Own

The temptation of gamification is to invent your own rule set (experience points, levels, achievements — design whatever you like). But there's a constraint here: this course already has a well-defined methodology of its own — **read → write → run → leave evidence** — and its lecture materials treat evidence as the endpoint of the learning loop.

So I mapped the level-completion criteria directly onto those four steps instead of creating a separate scheme:

| Action | XP |
|---|---|
| Finish reading the lecture | 10 |
| Hand-type and run the code successfully | 25 |
| Run this lesson's command from the repo root | 20 |
| Leave evidence | 30 |
| Answer a question correctly | 15 |

One level per 250 XP; clearing all levels in a stage unlocks the boss fight (12 questions, pass line at two-thirds); evidence is registered into the portfolio and can be exported.

Because the rules fit the course itself, users don't have to switch between two mental models — this was the decision I was most satisfied with in this project.

## 5. Verification: Turning "I Think It Works" into "I've Actually Tested That It Works"

The easiest way frontend projects fool themselves is: **open the page, click around a couple of times, think it's fine, and ship it.** This time I set four hard rules for myself.

### 1. Actually run frontend logic on the server with Node

Pure frontend logic is usually "only testable by opening a browser," but in fact, as long as you stub out the browser environment, you can run it directly on the server:

```js
// Core lines of tools/test-store.mjs
globalThis.localStorage = {
  getItem: (k) => (k in mem ? mem[k] : null),
  setItem: (k, v) => { mem[k] = String(v); },
  removeItem: (k) => { delete mem[k]; }
};
globalThis.window = globalThis;

new Function(fs.readFileSync('assets/store.js', 'utf8'))();   // actually run the business logic
const Store = globalThis.Store;
// Then assert directly: completion checks, XP calculation, badges, import/export…
```

This regression suite of 39 assertions **caught a real bug**:

> The original completion check determined whether a lesson had a quiz by asking "does this lesson have any answer records?" The absurd result: **a lesson with a question bank counted as completed once all four boxes were checked — as long as you didn't answer a single question.** The question-bank gate was effectively nonexistent, and it was completely invisible in the UI (the four boxes showed complete, the status showed passed).

The fix was to make the loading layer explicitly register the quiz index with the save layer, so the check priority becomes "registered index > local answer records":

```js
function hasQuizFor(path, l) {
  if (Object.prototype.hasOwnProperty.call(quizIndex, path)) return quizIndex[path] > 0;
  return !!(l && Object.keys(l.quiz).length);   // fallback path: has it been answered locally?
}
```

**This bug would never have been found without tests** — it only occurs on the "user never answers any question" path, and any developer testing manually will inevitably click on those two questions.

### 2. Data consistency tests

The second test file validates data specifically: every key in the question bank is a real lesson path, the number of questions per lesson, ID uniqueness, number of options, answer index range, question stem language, and the correspondence between course data and the question bank. 480 assertions, all green before committing is allowed.

### 3. Byte-for-byte online verification, and identifying "truncation false alarms"

Post-deployment acceptance can't just be checking that the homepage returns 200. My approach is to fetch the critical files from the live site and compare **sha256** with local copies.

The first verification produced a suspicious number: `data/course.json` was read as **99681 bytes** online, while local was **162046 bytes**.

This looks like a corrupted artifact, but it's actually the classic fingerprint of a single-transfer CDN truncation. The criteria for judgment are three:

- Fetch repeatedly and see if the size is **different every time** (the signature of truncation)
- Resume with `wget -c` and compare sha256
- Use `curl -r 0-0 -D -` to read the `content-range: bytes 0-0/162046` response header and get the true total size directly

The re-verification result: re-fetched four times, all 162046 bytes, sha256 identical to local, and the JSON parsed fine (all 20 stages / 523 lessons present). **The problem was in fetching, not the artifact.** If I had concluded "the file is corrupt" at that moment, I would have wasted an investigation round.

### 4. Don't trust the numbers self-reported by "subagents"

I split the question bank into three parallel AI subtasks. Each task reported back: "26 questions / 24 questions / 20 questions in total."

Before merging, I recalculated against the schema myself: **the actual result was exactly 2 questions per lesson, 62 questions in total.**

All three numbers were wrong (they had double-counted their own counts). If I had cited the self-reported numbers directly in the README, I would have fossilized false data into the project documentation. **Whenever a subtask delivers structured data, always recalculate yourself before merging: coverage, record count, uniqueness, field ranges — none can be skipped.**

## 6. Copyright and Boundaries

The upstream is MIT-licensed, which permits reuse, but "permitted" doesn't mean "you can copy whatever you want." This project handles it in three ways:

1. **Complete attribution**: `ATTRIBUTION.md` in the repository + the site footer + the "About" section on the homepage — all three state the upstream repository, the author, and the verbatim MIT license text
2. **Zero content mirroring**: only metadata is cited, deep links to the original text, no copying of diagrams, images, or UI copy
3. **No impersonation**: not using the upstream's name and logo as my own brand (MIT covers the code, not the trademarks), and explicitly stating that this project has no official relationship with the upstream

Another detail: I wrote the question bank myself (the upstream's quizzes are generated at runtime and there is no static question bank). The basis for the questions was the publicly available lecture notes, but the questions and explanations are paraphrases, not reproductions. Before merging I did a mechanical check — a "consecutive N-character overlap" scan of each question's text against the lecture notes. All three hits were English API/code snippets (function signatures, HTTP response headers and the like), technical terms that must appear verbatim, not copied body text.

## 7. Privacy and Security: Self-Discipline for Writing Public Technical Articles

This is a devlog, and it's very easy to slip and write things that shouldn't be written. Before publishing I went through the checklist item by item, with the rules being:

**Must not appear:**

- Internal IPs, hostnames, machine aliases
- Internal storage paths (mount points, volume directories, and the like)
- API keys / tokens / secrets / any service credentials and access links
- Internal tool names, task logs, session contents

**Must be generalized:**

- Environment descriptions only say "an internal Linux host" or "a server" — no models, addresses, or hostnames
- When network restrictions are involved, only describe the method and conclusion (which API was used, why small files were chosen over a full package) — no details of proxy schemes
- Configuration examples always use placeholders (`<token>`, `<host>`) — never paste real values

**A historical check I did in passing:** I scanned my previously published posts and confirmed that my earlier networking-related articles contained only generic configuration — no credentials, service addresses, or internal network information — nothing leaked. This kind of check is worth doing regularly, because many "seemingly harmless configuration snippets at the time" turn out to be sensitive only in retrospect.

---

## 8. Reflections

**Two things done right:**

1. **Check the upstream before starting work.** If I had dived headfirst into building a "learning website," two days of work would have produced a mirror site destined for the scrap heap.
2. **Copy the course's criteria.** Not inventing rules means users don't have to switch between two mental models.

**One thing not done well enough:**

As for the form factor, I actually finished building it before showing it to users. The cheaper approach is to **build a small sample of one stage first** (one stage, 20–30 lessons, real content + full interaction), confirm the form and information density, then scale up — in this project I only deep-built one stage before stopping, which is still within the line, but for the next project I plan to make this order a fixed rule.

---

## Summary

If you're also working on a similar project, the two most valuable takeaways from this post are probably:

- **Don't rebuild what the upstream already has**; list the upstream's features, and the room for differentiation will naturally emerge
- **Pure frontend logic can have real regression tests too**: stub out the browser environment, run assertions on the server — the time it saved me is the best argument
